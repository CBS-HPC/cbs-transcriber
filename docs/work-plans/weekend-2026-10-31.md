### Backup controls in Settings — design review

The current app exposes complete backup/restore through Library → Backups, with separate UCloud
connection, transfer, receipt and retention controls. Review a clearer Settings → Backup entry
that reuses this workflow and its existing safety checks rather than creating a second backend:

- Show the current library, backup destination/connection and separate last-local and
  last-verified-UCloud backup statuses, including incomplete transfers and actionable errors.
- Offer Create backup and Restore backup; restore selects a backup and independently saved
  receipt and creates a new local library without overwriting or merging the open one.
- Put UCloud destination, explicit whole-library transfer approval and receipt handling in a
  guided setup. Explain that the backup includes Protected projects, notes and Trash but no
  credentials. Preserve a separate trusted receipt; do not rely solely on package checksums.
- Keep manual retention preview and explicit Trash confirmation in advanced controls. Automatic
  schedules are a future design option, not existing behavior; define sleep, offline, active-job,
  failure and retention behavior before proposing one.
- Keep backup progress and failures visible in Activity; validate local and cloud status against
  actual durable receipts, not merely a button click. Reuse the existing UCloud connection while
  keeping backup transfer approval distinct from transcription approval.

Check whether Library → Backups should link to the same screen for discoverability. Real UCloud
transfer/restore and institutional storage, encryption, key custody and retention acceptance
remain open; this design does not claim those checks are complete.

### Anonymisation options to resolve

Use [the existing proposal](../proposals/anonymisation-2026-10-30.md) and the dated
[model survey](../evaluations/anonymisation-models-2026-10-30.md) as inputs. The weekend
design should cover local patterns/known names and manual span review first; an optional
UCloud detector can be represented by mocked suggestions. Detection suggestions never count
as researcher approval or a guarantee of anonymity.

- Bind spans to exact Working-version bytes/hash and Unicode character offsets. Refuse stale
  edits and conflicting/overlapping replacements. Matching a first name alone does not prove
  that two mentions refer to the same person; entity linking needs explicit review.
- Keep the source intact and generate a separate derived result. Preserve valid timing only
  for unchanged words; never invent timing for replacement text. Record reviewed decisions
  and method provenance separately from approved transcript content.
- Plan consistent project pseudonyms and researcher-added/rejected spans. Compare category
  tags with stable pseudonyms; leave the final default and re-identification-key retention
  policy open rather than choosing them silently.
- Test the proposed redacted-export allowlist against hidden originals, original word maps,
  speaker names, filenames, notes, report metadata and retained history. A renamed visible
  passage is insufficient if another exported field still identifies someone.
- Treat reversible pseudonymisation, irreversible text redaction and audio/video redaction
  as different scopes. Transcript processing alone does not anonymise the recording or its
  metadata. Encryption, key custody and retention need a separate CBS IT/DPO decision.

The synthetic demonstration may use disposable data and in-memory mappings only. Production
storage, model integration and processing of real research interviews need a separately
accepted design; the existing proposal's open decisions remain open.

Keep the running app and active jobs intact. Merge/restart only under existing authorization,
after the backend is idle, a verified backup exists and preservation checks are ready; otherwise
leave the build ready on its branch. Retain the old library copy. Never synchronize the shared
running environment, change repository visibility/licensing or publish a release implicitly.

No paid API calls, real UCloud allocations, private uploads or large model downloads are part
of unattended offline work. Real device/provider acceptance requires its own concrete scope.
Weekend execution needs the computer awake and the execution environment available; preserve
checkpoints so credit/runtime interruptions do not lose work.

The final handoff must state: exact source/branch and running build; changes and verified
findings; test commands/results and limits; remaining blockers; work awaiting a real device,
provider budget or human decision; and the next smallest task. Do not claim that an audit
proves there can be no further errors.
