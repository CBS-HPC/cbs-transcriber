# 0122 — Explicit standalone UCloud Runtime preparation

A manual **Check UCloud again** action can prepare a missing base CBS Runtime when
the saved automatic-preparation choice permits it. Opening Settings, periodic checks,
and saving the checkbox do not start preparation. The action rechecks the saved consent
and the displayed connection fingerprint before admitting work; an unavailable or changed
connection is never silently retargeted.

Preparation has its own durable, library-level Activity owner rather than a fictional
recording. Schema 16 retains frozen connection choices and a credential-free allocation
journal. Its shared capacity accounting, submission intent, uncertain outcomes and known
remote identity survive restart. Never automatically repeat an uncertain submission.
Stop records intent before network control, acts on the recorded allocation independently
of a busy preparation lane, and releases capacity only after a terminal observation.
Retry, reconciliation and cleanup are scoped to the owned operation; corrupt owners retain
their evidence without starving others. Restored owners remain inert.

Activity shows recent settled history and every unresolved or unverified obligation. A
new explicit preparation may create a visible successor to a settled owner when the base
runtime is again missing; active or uncertain work on the same physical target is deduplicated.
The preparation includes base runtime packages, CUDA checks and existing baseline public
caches. Additional selected ASR profiles and gated speaker models remain separate readiness
checks. No recording is uploaded for this operation. Actual UCloud preparation and platform
acceptance remain distinct from synthetic tests.
